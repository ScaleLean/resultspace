# Project and claim provenance invariant

Journal has one canonical project. When `about_id` identifies a project, explicit `project_id` must match it. When it identifies a scoped fact/knowledge/other record, explicit project must match that record's project. Creation fills omitted project from `about`. Journal `project_id` and `about_id` are immutable after creation, including absent or historical anchors; generic patch and undo cannot change them, and archive/restore preserves the body. Corrections append a new attributed entry. Content edits remain allowed. A scoped claim cannot be moved to a different project while Journal records explicitly anchor it to the prior one: append a corrected claim and Journal entry instead. Company-wide claims may deliberately be cited by multiple projects; these citations never copy Journal entries into a second log.

Historical entries are not rewritten on migration/read. Missing project links resolve through `about` at read time; contradictory legacy links remain available by key/history and in the company Log, with a scope warning. They have no canonical project and appear in `scope_conflicts`, outside both focused project logs. An explicit scope correction appends a new attributed entry, preserving the original anchors and history. Canonical filtering precedes pagination; creation order is independent of subsequent edits.

Current claim provenance comes from sequential revision bodies, not the record's last editor or a historical `changed` list. A fact assertion comprises subject, predicate, value type/value, scope, unit, observation time and project. Knowledge comprises freeform body/text and project (title is assertion content when there is no body). Journal assertion content comprises type/title/detail/text/about/project. Source/citation edits have separate provenance; metadata-only edits remain last-edit history. Undo is a new assertion only when it changes assertion content. Original actor/time/body, assertion actor/time/revision, last edit and citation change are exposed independently in record/project context and web reads. A citation is supplied evidence, not independent verification.

No workflow machinery was added. Schema 6 gives new issue notes a distinct identity so legacy issue semantics remain preserved. See [migration and rollback](deploy/MIGRATION.md) and [installed-client coordination](deploy/INSTALLED-CLIENT-MIGRATION.md). Release remains gated on independent review and the operator's consistent live-copy backup/restore rehearsal; no installed clients were changed.
